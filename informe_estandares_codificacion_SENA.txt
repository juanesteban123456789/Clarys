8. ESTANDARES DE CODIFICACION RECOMENDADOS

Nombres de variables:
- Usar camelCase.
- Ejemplos: productName, salePrice, customerPhone, minStock.

Nombres de clases:
- Usar PascalCase.
- Ejemplos: ProductFormActivity, InventoryMovement, ProductRepository.

Nombres de metodos:
- Usar camelCase con verbos claros.
- Ejemplos: saveProduct, confirmSale, loadProducts, refreshCart.

Nombres de constantes:
- Usar MAYUSCULAS_CON_GUION_BAJO.
- Ejemplos: EXTRA_PRODUCT_ID, SALE_STATUS_CONFIRMED, DEFAULT_CURRENCY.

Organizacion de paquetes:
- com.clarys.app.activities o com.clarys.app para Activities.
- com.clarys.app.model para modelos.
- com.clarys.app.data para datos temporales o mock.
- com.clarys.app.repository para repositorios reales.
- com.clarys.app.service para servicios/API.
- com.clarys.app.ui para adaptadores y componentes UI.
- com.clarys.app.utils para utilidades.

Comentarios:
- Usar comentarios solo cuando ayuden a entender una regla de negocio o logica
  no evidente.
- Evitar comentarios que repitan exactamente lo que hace una linea.

Indentacion:
- Usar 4 espacios en Java.
- Mantener XML ordenado y legible.

Longitud recomendada de lineas:
- Entre 100 y 120 caracteres.

Buenas practicas para Activities:
- Las Activities deben manejar principalmente UI y navegacion.
- Evitar concentrar demasiada logica de negocio en Activities.
- Delegar datos a repositorios o servicios.

Buenas practicas para XML:
- Usar IDs descriptivos.
- Ejemplos: inputProductName, buttonConfirmSale, recyclerSaleProducts.
- Mover textos visibles a strings.xml.

Buenas practicas para backend:
- No guardar claves secretas directamente en codigo fuente.
- Centralizar URLs, endpoints y claves publicas.
- Usar repositorios: ProductRepository, SaleRepository, InventoryRepository.
- Manejar errores de red y estados de carga.

10. RESUMEN PARA DOCUMENTO SENA

El proyecto Clarys debe adoptar estandares de codificacion propios de una
aplicacion Android nativa desarrollada en Java y XML. Las clases deben nombrarse
en PascalCase, los metodos y variables en camelCase, y las constantes en
MAYUSCULAS_CON_GUION_BAJO. La estructura debe mantenerse organizada por
responsabilidades, separando Activities, modelos, adaptadores, repositorios y
servicios. Los textos visibles deben ubicarse en archivos de recursos como
strings.xml, mientras que valores fijos como estados, filtros, claves de Intent
y tipos de movimiento deben definirse como constantes. Estos estandares permiten
que el codigo sea mas legible, mantenible, escalable y facil de integrar
posteriormente con backend, base de datos o servicios externos como Supabase/API.
